# Songs

Design of songs in webpresenter: what a song is, how its lyrics, slides, recordings and timing
are modelled, how the LouvorJA export is converted, and how the future automatic pipeline
(audio → lyrics, timing and backing track) plugs in without reshaping anything.

Status: phases 1–5 implemented (see the end of this document); the pipeline is prepared, not built.

## Goals

- A song can be presented **with a recording** (slides advance by themselves, in sync with the
  audio) or **without** (band plays live; the operator advances slides).
- Lyrics are **text**, rendered by the player over a background with a configurable theme.
  Correcting a word or changing the font never requires regenerating anything.
- The same lyrics serve several recordings (sung, playback/instrumental, another arrangement),
  each with its own timing.
- Every piece of data records **where it came from** (import, typed by a person, generated by the
  pipeline) and whether it was **reviewed**, so automatic results can be trusted gradually.

## Model

```
Song ─┬─ Lyrics (one document, versioned)
      │    ├─ parts:  Verse 1, Chorus, Verse 2, Bridge …   (unique content)
      │    │    └─ slides: lines of text shown together
      │    └─ order:  [V1, C, V2, C, B, C]                  (singing order, repeats allowed)
      ├─ Recordings: Sung, Playback, …  (library audio/video)
      │    └─ Timing: start time of every slide occurrence in the order
      ├─ Background: library image or video (per song, optional per part)
      └─ Collections: "Hinário Adventista" nº 123, "CD Jovem 2012" faixa 4 …
```

### Song

| Field | Notes |
|---|---|
| title, alternative titles | Searchable, accent-insensitive. |
| language | `pt`, `es`, … |
| authors, copyright | Free text, shown on the first slide if the theme wants it. |
| collections | Many-to-many with a number/track (hymnal number, album track). |
| background | Default library image/video for its slides. |
| source | `MANUAL`, `IMPORT` (with origin, e.g. `louvorja`, and external id), `PIPELINE`. |
| status | `DRAFT` (incomplete or generated, needs review) or `READY`. |

### Lyrics

Stored as one JSON document per song (read and written as a whole; history kept by version).

- **Parts** are the unique blocks of the song (`VERSE`, `CHORUS`, `PRE_CHORUS`, `BRIDGE`, `INTRO`,
  `OUTRO`, `TAG`, `INSTRUMENTAL`, `OTHER`) with a label ("Estrofe 1", "Coro"). A part has one or more
  **slides**; a slide has lines and an optional **cue** ("Homens:", "Todos:"). `INSTRUMENTAL` parts
  have no text: the slide shows only the background.
- **Order** is the sequence of part ids as sung. A chorus sung three times is one part referenced
  three times, so correcting it once fixes every repetition.
- The ordered, expanded list of slides is called the **slide sequence**; it is what the player
  shows and what timing refers to.

Why this shape: it is what worship tools converge on (verse order), it removes the physical
duplication of the LouvorJA data, it lets a band skip or repeat parts, and it is exactly the
structure the pipeline produces (transcribe lines → group into parts → detect repeats).

Interchange: import/export as **ChordPro** (`{start_of_chorus}`…) for people who edit lyrics as
text; chords can be added later without changing the model (a line can carry chord positions).

### Recordings

A recording is a library media asset (audio, or video with sound) attached to the song:

| Field | Notes |
|---|---|
| kind | `SUNG`, `PLAYBACK` (instrumental/backing track), `OTHER`. |
| media | Library asset (`AUDIO` or `VIDEO`), so pre-cache and S3 work unchanged. |
| source | `IMPORT`, `MANUAL` (uploaded), `PIPELINE` (e.g. Demucs-generated playback). |

### Timing

Per recording, one JSON document:

```json
{ "lyricsVersion": 3, "source": "IMPORT", "reviewed": true,
  "cues": [ { "slide": 0, "startMs": 17000 }, { "slide": 1, "startMs": 36000 } ] }
```

- `slide` is the index in the slide sequence for that lyrics version. If the lyrics change
  structurally, timing referring to an older version is flagged for review instead of drifting.
- Optional finer data (`lines`/`words` with times and confidence) can be added by the pipeline;
  the player only needs slide cues.
- No timing → the song can still be presented, advanced by the operator.

### Library integration

Recordings and backgrounds are ordinary library assets with a **purpose** (`GENERAL`,
`SONG_AUDIO`, `SONG_BACKGROUND`). The library page lists `GENERAL` by default so thousands of
song files do not bury everyday media. Imports upload with `deduplicate=true`: a file whose
SHA-256 is already stored is reused instead of stored again (uploads from the web app always create
a new item, as people expect).

## Presenting

- New event item type **SONG**: song + chosen recording (or none) + optional background override.
- Player: downloads the recording and background with the rest of the event (pre-cache), plays
  the audio and advances slides at the cue times; without a recording it shows the first slide and
  waits for `NEXT_SLIDE`/`PREVIOUS_SLIDE`.
- Live page: the slide sequence of the song on screen, current slide highlighted, click to jump
  (also during playback, re-syncing the audio to that cue). Musicians see the lyrics and what is next.
- Theme (font, size, colour, shadow, position, safe margins) per player, editable in Dispositivos.

### As implemented (phase 5)

- Event items of type `SONG` reference a song and a recording (or none). Players receive the whole
  song in `PREPARE` (slides, audio, cues, background) and pre-cache audio and background.
- Starting a song (Próximo, or a click on the item) plays it **from the beginning**: with timing,
  only the background shows until the first cue (the intro). Choosing a slide (`SLIDE` command,
  click in the live page) shows it and jumps the audio to its cue.
- Inside a song, Próximo/Anterior move slide by slide; after the last slide Próximo goes to the
  next item. Timed songs advance on the players; the server follows their reports so every web
  client shows the slide on screen. Pause/continue work as for any audio.
- A player joining during a song starts at the current slide and audio position.
- Song backgrounds cover the whole output (cropped, they are decorative); the text is white with
  a shadow over a darkened background. Not yet: video backgrounds, configurable theme, chords.

## Pipeline readiness (not implemented now)

The pipeline only writes into the structures above, so it can be added step by step:

| Step | Input | Output written to | Tool |
|---|---|---|---|
| Separate | SUNG recording | new `PLAYBACK` recording (`source=PIPELINE`) | Demucs |
| Transcribe | SUNG recording | draft lyrics (`DRAFT`), lines with times | Whisper |
| Align | lyrics + SUNG recording | timing (`source=PIPELINE`, `reviewed=false`) | WhisperX forced alignment |
| Segment | timed lines | parts, slides and order (repeat detection) | rules |
| Transfer | SUNG timing | PLAYBACK timing (same arrangement, audio cross-correlation) | rules |

Each step is a job (queued, running, done, failed) handled by Python workers through RabbitMQ, as
in `architecture.md`; results stay `DRAFT`/`reviewed=false` until a person accepts them in the
song editor. Nothing in the song model changes when the pipeline arrives.

## LouvorJA conversion

The export (`tools/louvorja/export_louvorja.py`) produces songs with a flat list of timed slides.
Conversion to the model above:

1. Split the slide list into blocks at instrumental breaks (empty slides).
2. Identical blocks become one part referenced several times in the order; the most repeated
   block is labelled "Coro", the others "Estrofe 1, 2 …" (editable later).
3. Empty slides become `INSTRUMENTAL` parts (background only).
4. Slide times become timing cues of the `SUNG` recording; `playbackStart` times (when present)
   become the cues of the `PLAYBACK` recording.
5. The most common slide background becomes the song background; collections and album tracks
   become song collections with numbers.
6. Songs are created with `source=IMPORT`, `origin=louvorja`, `status=READY`, `reviewed=true`.
   Re-running the import is idempotent (matched by external id; files by SHA-256).

## Implementation phases

1. **Production stack and replication**: `deploy/compose.prod.yaml` (PostgreSQL, Keycloak in
   production mode, SeaweedFS, server with the web app, reverse proxy), `.env`, backups;
   bidirectional `weed filer.sync` to a second SeaweedFS, tested with two local instances.
2. **Songs module (server)**: model, migrations, REST API, library purpose and SHA-256 de-duplication.
3. **LouvorJA import** into production: files to SeaweedFS through the library, songs and timing.
4. **Songs in the web app**: song list and search, song view (parts, order, timing), editor.
5. **Songs live**: SONG event items, player rendering with theme and timed advance, live page
   slide control.
